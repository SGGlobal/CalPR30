## Closed synthetic input contract

SyntheticInput includes sender, role, recipient, project/task/checkpoint/assignment/message/idempotency IDs, a positive integer sequence, UTC timestamps, and a plain scalar-only payload.

| Event | Exact payload keys | Actor/role to recipient |
| --- | --- | --- |
| assignment | type, objective, evidence_id, base_sha | chief/chief to jason |
| implementation | type, evidence_id, implementation_sha | jason/implementer to skippy |
| correction | type, evidence_id, implementation_sha | jason/implementer to skippy |
| review | type, evidence_id, implementation_sha, verdict | skippy/reviewer to jason |

The objective and evidence_id must be nonempty and have no surrounding whitespace. Bound SHA fields require exactly 40 lowercase hexadecimal characters. The only review verdicts are approved and changes_requested. All extra keys and unknown types are denied. SHA formatting does not prove commit existence or independent review.

The simulator constructs **new** SignedEnvelope test messages from copied typed inputs. It uses B1 canonical bytes and Ed25519 signing keys with mandatory test-b2b2- key ID prefixes. The prefix is a segregation convention, not operational key attestation. Fixture signatures do not authenticate real agents or Chief authorization.

## Deterministic workflow table

| Current in-memory state | Event and preconditions | Next state |
| --- | --- | --- |
| EMPTY | assignment, sequence 1 | AWAIT_IMPLEMENTATION |
| AWAIT_IMPLEMENTATION | implementation, unused SHA | AWAIT_REVIEW |
| AWAIT_REVIEW | review approved, latest SHA | CLOSED |
| AWAIT_REVIEW | review changes_requested, latest SHA | AWAIT_CORRECTION |
| AWAIT_CORRECTION | correction, unused SHA | AWAIT_REVIEW |
| CLOSED or disallowed transition | anything | DENY |

This harness simulates exactly one project/task/checkpoint/assignment stream. Each reserved transition consumes one sequence; exact redeliveries are only duplicate *candidates* and still require current B2.1 signature, HALT, evidence and durable identity checks. Identical duplicates never advance the in-memory workflow; conflicting IDs fail. In B2.1, the durable identity namespace is project+task, including reuse across checkpoints.

The correction_request event is not silently accepted or relabeled. A *new test-only* review with verdict changes_requested models that workflow step; no legacy signed message is converted.

## Explicit test-only authorities

SyntheticBridgeSimulator requires an injected matching test-only TrustRoot and signing-key map, a contextual test fixture policy, an evidence verifier, and an injected HALT provider. No default acceptance is permitted.

The existing B2.1 EvidenceVerifier interface accepts only kind, assignment_id, bound_sha, evidence_id, and now. It does not authenticate project/task/action/sender/role as a production proof. An injected string of verified is a synthetic test result, **not** real Chief or SKIPPY authorization.

The fixture policy is given a separate scalar-only copy of the validated input, never the internal plan payload object. Callback-visible field or payload changes are detected and rejected before signing or gate reservation. next_snapshot and the receipt fingerprint stay bound to those unchanged internally validated fields. Altered policy input is never authorized and is never used to recompute a plan.

B2.1 OfflineAdmissionGate.reserve verifies freshly signed messages, the sender matrix, evidence, SHA and sequence, and persists RESERVED only. RESERVED is **not** ACCEPTED, ledger appended, dispatched, deployed, or traded. The simulator must never import or call OfflineAuthenticatedAdapter.accept, protected ledger writers, network transports, or order execution.

## Failure and restart model

The workflow tracker is in-memory only. Simulated process restart invalidates it. Creating a new simulator requires a fresh disposable SQLite database; existing state is not resumed as authority. The pre-construction exists()/wal/shm freshness check is not an atomic cross-process exclusive store-creation lock and must not be treated as cross-process exclusivity. Session close is serialized with the simulator lock by work order 6847721660: close_session() and the legacy invalidate_for_restart() (which now delegates to close_session(timeout=None) and returns a typed CloseResult) wait for an active transition instead of racing it, and a same-thread close from a callback is refused. This is synthetic-harness session control only; it is not cancellation, operational recovery or crash-safe session control. Before that work order invalidate_for_restart did not acquire the simulator lock, so a concurrent invalidation could race an in-flight simulate() call (characterized by work order 6846823630, see below). Gate errors, including indeterminate commit, invalidate the session without replay. Existing PENDING or UNCERTAIN reservations deny B2.1 initialization; they are not evidence that a ledger write was absent.

This phase performs **zero ledger appends**. Real post-ledger-append crashes, cross-store reconciliation, manual recovery and authoritative HALT/ledger atomicity must be studied in a different, separately authorized security milestone. The injected HALT probe has an unresolved probe-to-commit race. SQLite reservations are not a tamper-evident audit ledger.

## Single active transition and reentrancy (work order 6845727928)

Finding 6845540923: simulate() holds a reentrant RLock while it calls the caller-supplied fixture policy, and the gate calls the injected HALT and evidence fixtures during reserve. A callback holding the simulator could re-enter simulate() on the same thread. At e54ca6e a one-shot recursive policy made the inner call reserve and advance the snapshot, after which the outer call (planned from the earlier snapshot) reached the gate, received an unexpected duplicate, raised AdmissionError and invalidated the session.

Contract: one session has at most one active transition. simulate() checks and sets an in-progress flag while holding the existing RLock and clears it in a finally block on every return and exception path. A nested call on the same thread is rejected with the deterministic reason "reentrant simulate rejected" before planning, signing or gate access, and it changes no snapshot or reservation row. The RLock is kept: a plain non-reentrant lock would deadlock same-thread recursion. Another thread never sees the flag set, because the flag is only set and cleared while the lock is held; such a call waits for the lock and runs afterwards (normal cross-thread serialization). Gate exceptions still invalidate the session without retry, and the flag is cleared afterwards.

Outer continuation: the outer call continues after a rejected inner attempt and is decided by its own plan, policy result and gate result. Because the rejected inner attempt changed nothing, the outer plan is still based on the current snapshot, and a valid outer call commits exactly one reservation row whose receipt fingerprint matches the outer input. Separately, the simulator records the snapshot it planned from and refuses to proceed if that snapshot changed during the policy call (reject before signing) or during reserve (raise AdmissionError and never apply the stale plan); both invalidate the session.

Limits: this is a test-fixture consistency control, not a sandbox. In-process code can bypass it, for example by calling the private _simulate_locked method; the snapshot-change checks then fail closed, but a reservation made by the bypassing call may already be committed. The guard adds nothing for cross-process exclusion, durable T25 cross-checkpoint identity, store-creation freshness or concurrent invalidate_for_restart races; those constraints remained open as stated above (the invalidation race was later addressed within this simulator by work order 6847721660). The direct-gate T25 and separate-process evidence of work order 6846218272 is independent of this guard.

### Observed current behavior (characterization, not safety)

At this source invalidate_for_restart() writes the invalidation flag without acquiring the simulator lock and returns None. simulate() reads the flag once, at the start of _simulate_locked, before planning. An invalidation that lands after that read does not stop, cancel or roll back the active transition. A passing characterization test proves only that the interleaving reproduces; it is not a safety property, a fix or the proposed semantics below. The expectations were first observed on authentic Windows with a separate probe and then asserted unchanged.

### Design proposal: serialized session close (preferred; reviewed design, implemented later by work order 6847721660)

Revision (work order 6847360432): this proposal is revised to resolve the four precision findings of design review 6847235164 (neutral timeout result and timeout validation, active-before-terminal ordering, corrected caller inventory and migration, closed typed outcomes with the competing-close precondition), with the acceptance specifications updated to match. It remains DESIGN ONLY. No simulator, contract or test change is made, close_session() does not exist at this source, and nothing in this subsection describes current behavior; current behavior is only what the characterization subsection above records.

Scope: this synthetic, non-resumable harness only. The proposal serializes close with active transitions; it does not cancel them.

**State.** One terminal "closed" state, entered by an explicit close or by the existing internal fail-stop invalidations (gate exception, snapshot change, unexpected outcome). The proposal reuses the existing _invalidated flag as the terminal flag and the existing _in_progress flag. Both are read and written only while holding the existing simulator lock: the internal invalidations already run inside the locked transition, and invalidate_for_restart(), the one unlocked writer at this source, is migrated as described below. Nothing clears the terminal flag: no reopen, no reset and no reuse of a closed session.

**Closed typed outcome set.** Proposed names follow the repository's existing `(str, Enum)` convention with upper-case members (for example HaltStatus and CheckpointState) and the simulator's frozen-dataclass result convention (SimulationResult):

```python
class CloseOutcome(str, Enum):
    CLOSED = "CLOSED"
    ALREADY_CLOSED = "ALREADY_CLOSED"
    REFUSED_ACTIVE_TRANSITION = "REFUSED_ACTIVE_TRANSITION"
    LOCK_TIMEOUT = "LOCK_TIMEOUT"


@dataclass(frozen=True)
class CloseResult:
    outcome: CloseOutcome
    reason: str
    # __post_init__ raises TypeError unless type(outcome) is CloseOutcome
    # and type(reason) is str; plain strings are never accepted as outcomes.
```

These four members are the complete outcome set; there is no free-form or permissive outcome string. CloseResult construction rejects a plain string or any other type for outcome, so a misspelled or ad hoc outcome cannot be produced or accepted. Because the `(str, Enum)` convention makes members compare equal to their string values, callers and tests check `type(result.outcome) is CloseOutcome` and compare by identity (`result.outcome is CloseOutcome.CLOSED`), never by string. Frozen means attribute assignment raises; that is a fixture-consistency property, not a sandbox against in-process object.__setattr__. Only CLOSED and ALREADY_CLOSED are successful outcomes. REFUSED_ACTIVE_TRANSITION and LOCK_TIMEOUT are returned values meaning only that this call did not close the session. Invalid arguments raise TypeError or ValueError, and lock-acquisition exceptions propagate; neither produces a CloseResult, neither is a successful close outcome, and no exception is ever converted into an outcome.

**Timeout validation (before any lock acquisition or state access).** close_session(timeout=None) validates timeout first, in this order. On any failure it raises without acquiring or releasing the lock, without reading or writing _invalidated or _in_progress, and without creating a result.
1. None means unbounded blocking acquisition.
2. type(timeout) must be exactly int or exactly float. bool (an int subclass), any int or float subclass, str, Decimal, Fraction, numpy scalars and any object implementing __index__, __int__ or __float__ raise TypeError. No coercion is performed and no custom numeric protocol method is invoked.
3. For a float, NaN, +inf and -inf raise ValueError (math.isfinite is checked before any range comparison).
4. The value must satisfy 0 <= timeout <= threading.TIMEOUT_MAX, otherwise ValueError. The comparison is made on the original int or float, which Python compares exactly without converting the int, so a huge int such as 10**1000 is rejected with ValueError by this bounded comparison first and never reaches float(), which would raise OverflowError. Only an in-range value is passed to acquire. -0.0 compares equal to 0 and is treated as zero.

The same validation runs on every path, including a same-thread call from inside an active transition: an invalid timeout raises there too, before the lock is touched, with both flags unchanged.

**Acquisition.** timeout=None uses self._lock.acquire() (blocking, unbounded). timeout == 0 uses self._lock.acquire(blocking=False), a single nonblocking attempt. A positive timeout uses self._lock.acquire(timeout=timeout), a bounded wait. If acquire returns False, the call returns CloseResult(CloseOutcome.LOCK_TIMEOUT, ...) at once without reading or writing any session state. If acquire raises (for example a KeyboardInterrupt or other interruption delivered while waiting), the exception propagates unchanged with no close result and no state change, and nothing is released because nothing was acquired. Once acquire returns True, all further work runs inside try/finally and the lock is released in finally on every return and exception path. The timeout limits only the lock wait; it is not a hard end-to-end scheduling deadline. Thread scheduling, the GIL and the short locked section mean the call can return later than the timeout, and timeout=None waits as long as the active transition or other lock holder.

**LOCK_TIMEOUT meaning (neutral).** LOCK_TIMEOUT means only that this call did not acquire the lock and performed no close. It makes no claim about the session. The lock may have been held by an active transition, by another close_session() call, or by any other lock holder, so LOCK_TIMEOUT is not "active transition" and must not be conflated with REFUSED_ACTIVE_TRANSITION, which is decided only under the lock. While this call waited, another closer or an internal gate-error invalidation may already have closed the session, so the session's terminal and active state is unknown to this call and is not guaranteed OPEN. The implementation must not inspect _invalidated or _in_progress without the lock to refine this result. LOCK_TIMEOUT does not certify quiescence. A caller that needs a definite state calls close_session() again, for example with timeout=None.

**Decision order under the acquired lock (active before terminal).**
1. If _in_progress is True, return CloseResult(CloseOutcome.REFUSED_ACTIVE_TRANSITION, "close refused while a transition is active on this thread"). This check comes first and applies even if _invalidated is already True, for example when an internal invalidation path has set the terminal flag while the outer transition is still active. It changes neither flag, does not certify quiescence and does not affect the outer transition. Because an active transition holds the lock for its whole duration, a lock holder that observes _in_progress True is necessarily the active thread itself (RLock reentrancy), so this is the same-thread path.
2. Else, if _invalidated is True, return CloseResult(CloseOutcome.ALREADY_CLOSED, ...).
3. Else set _invalidated = True and return CloseResult(CloseOutcome.CLOSED, ...).

Only a lock owner that has observed _in_progress False may return CLOSED or ALREADY_CLOSED, and only those two outcomes certify quiescence. No branch cancels a transition, reopens the session or clears the terminal flag.

**Linearization point.** For CLOSED, the write of the terminal flag in step 3 while holding the lock; for ALREADY_CLOSED, the locked read in step 2. Every transition that acquired the lock before that point has completed, including any reservation row it committed, before close_session() returns. Every public simulate() that acquires the lock after that point reads the flag first and is denied before planning, signing or gate access, with zero new rows.

**Return meaning.** CLOSED or ALREADY_CLOSED means: this call held the lock with no transition active; every earlier transition had finished; every future public simulate() call is denied. CLOSED additionally means this call performed the close; ALREADY_CLOSED means an earlier explicit close or internal invalidation did. Neither means that no reservation was written after the close was requested: a transition that acquired the lock first, including one that started after the close was requested, may commit while the close waits. Over the lifetime of one session at most one call can ever return CLOSED. REFUSED_ACTIVE_TRANSITION and LOCK_TIMEOUT mean only that this call did not close the session.

**Explicit non-goals.** Not cancellation, not immediate HALT, not a bounded end-to-end latency (the timeout limits only the lock wait, and timeout=None waits as long as the active transition, including slow callbacks), not rollback of committed rows, not crash recovery, not reopening. No fairness claim: RLock acquisition order is not FIFO, and the close does not exclude calls that acquire the lock first. No in-flight cancellation design across the frozen B2.1 gate or SQLite boundaries: the HALT/evidence callbacks and BEGIN IMMEDIATE/INSERT/commit run inside protected gate code, and interrupting them could leave an indeterminate commit.

**Same-thread callback close.** A close called on the thread that is executing the active transition (from the fixture policy, or from a HALT or evidence callback inside reserve) acquires the RLock immediately because an RLock is reentrant, whatever the timeout (including 0); RLock alone therefore cannot refuse or wait. The _in_progress-first rule makes it refuse deterministically with REFUSED_ACTIVE_TRANSITION, including when the terminal flag is already set. Both flags are unchanged, and the outer transition is unchanged: same plan, policy result, gate call, rows and snapshot as a run without the close. A returned result, not an exception, is proposed because the simulator and gate convert callback exceptions into different outer outcomes ("synthetic signing/policy failed closed", "HALT probe failed closed", "evidence verification failed closed"), which would change the outer transition. The timeout is still validated first on this path, so an invalid timeout raises TypeError or ValueError inside the callback before the lock is touched; what the outer transition then does with an exception the callback does not catch is the existing callback-exception behavior, not a close outcome.

**Alternative: deferred close.** A same-thread close records a pending request; the outer transition completes unchanged and the finally block of simulate() applies the close under the lock on every return and exception path. **Specified edge behavior (proposed).**
- Repeated close (sequential, idle): the first returns CLOSED; every later call returns ALREADY_CLOSED, raises nothing and changes nothing.
- Competing closes from several threads: serialized by the lock, and at most one returns CLOSED. Precondition for exactly one CLOSED: the session is initially open (no earlier explicit close or internal invalidation), no concurrent transition internally invalidates it, and every closer uses timeout=None so none returns LOCK_TIMEOUT. Then exactly one returns CLOSED and the others ALREADY_CLOSED, in unspecified order. Without that precondition, all closers returning ALREADY_CLOSED is legitimate (for example when a gate-exception invalidation linearizes first), and with finite timeouts some closers may return LOCK_TIMEOUT.
- Close racing a new simulate(): whichever acquires the lock first runs first; if the close linearizes first, the simulate is denied with zero plan/sign/reserve calls. No ordering is promised.
- Policy denial, policy exception or gate rejection in the active transition: the close waits for that outcome, which is unchanged, then returns CLOSED.
- Gate exception in the active transition: the outer simulate() raises the same exception type and message as without the close; the existing internal fail-stop invalidation applies first; the waiting close then returns ALREADY_CLOSED and raises nothing. The close never swallows, converts or re-raises the gate exception.
- Same-thread close from a callback, including when the terminal flag is already set while the transition is still active: REFUSED_ACTIVE_TRANSITION. Refusal does not alter the transition's later success or failure. After the transition ends, an external close returns CLOSED, or ALREADY_CLOSED if the transition internally invalidated.
- Nested simulate() from a callback after a refused close: still rejected as reentrant (unchanged).
- Stuck callback: with timeout=None an external close blocks as long as the callback. With a finite timeout it returns LOCK_TIMEOUT, which is neutral: this call performed no close, nothing was cancelled, and the state is unknown to this call (no claim that the session is open). A later close returns CLOSED or ALREADY_CLOSED depending on what happened meanwhile. A permanently stuck callback leaves both stuck; terminating the process is a crash outside this model.

### G1. The stronger requirement and the three clear-related seams

**Requirement (Alternative A, carried from 6816825101 C-2 and 6834104402 P2.4):** every ambiguous result stops all future admission, by every participant, until manual recovery.

**Two different facts.** The *actual commit outcome* is a property of durable storage: a commit either landed or did not (for SQLite this may be settled only when the next connection opens the file and handles any hot journal). The *caller-observed outcome* is what the calling instance can prove: **confirmed** (every conditional statement had rowcount 1 and COMMIT returned), **confirmed rolled back** (failure raised before COMMIT was issued and ROLLBACK returned), or **ambiguous** (anything else, including COMMIT or ROLLBACK raising, and a process that dies after issuing COMMIT). Ambiguity is knowledge held only by the caller; it is not written anywhere by the act of failing. A fresh process sees only the actual outcome.

| Seam (6838692613 §4) | Rollback-before-commit (confirmed) | Landed, then raised (caller: ambiguous) | Not landed, raised after COMMIT issued (caller: ambiguous) | What a fresh process / cooperative contender observes |
| --- | --- | --- | --- | --- |
| S8 guard commit (sets G) | no G, no gate call; instance poisoned | G durably present; no gate call | no G; no gate call | Landed: `stopped = 1`, contender refused at the ADP:531-535 check or S3. Not landed: state identical to "no attempt"; contender proceeds. |
| S10 definite-rejection cleanup (rejected receipt + exact clear of G) | G kept, no receipt; contender refused | G cleared and receipt present | G kept, no receipt | Landed: `stopped = 0`, receipt present; contender **proceeds**. Identical to a confirmed rejection. |
| S13 W3 (ACCEPTED, receipt, sequence, assignment + exact clear of G) | PENDING and G kept; contender refused | the whole W3 is durable, G cleared | PENDING and G kept | Landed: identical to a confirmed acceptance; contender **proceeds** although the originating caller observed failure. |

In each landed-then-raised row the originating instance is poisoned, but the poison is a per-instance in-memory latch (6838692613 §4B.4), the existing adapter lock is a `threading.Lock` (ADP:79, ADP:520), and neither is visible to another process. That is why §G records that the three-path design does not meet the requirement.

**Existing anti-pattern, for reference.** Legacy `accept()` handles a failed W3 by rolling back and then writing `UPDATE fail_stop SET stopped = 1, reason = ? WHERE singleton = 1` to the same receipts store (ADP:705-716); if that write fails it is swallowed (ADP:717-718, comment "next admission will reconcile"). This is exactly "a later write to the same failing store", and it is unconditional, so it would also overwrite a foreign stop reason or a proposed G. Nothing below relies on a write after an ambiguous result.

### G2. Proposed persistent mechanism: pre-armed stop with a separate release commit (PROPOSED, OUTSIDE IMPLEMENTATION AUTHORIZATION)

**Idea.** Never let an admission-effect commit change the global stop. The stop is armed durably *before* any admission effect, every effect commit runs while it is present and never touches it, and it is removed only by a dedicated **release commit** that carries no admission effect and is issued only after every effect commit is **confirmed**. Then an ambiguous effect commit leaves the stop present on both branches, with no later write needed.

1. **Store and row.** Reuse the receipts database `fail_stop` singleton (ADP:381-390) with the 6838692613 §4B.2 nonce-bearing G in `reason`. No new database; this avoids adding a cross-database step to the stop itself. A separate stop database was considered and rejected: it adds a cross-database window (no cross-db atomicity, §9) and does not remove either counterexample in G3.
2. **Ownership.** As in 6838692613 §4B.2: a fresh per-call nonce held in memory, control flow that never adopts a stored G (constructor, restart and resubmission never read `reason` to decide anything), exact conditional updates with rowcount checks, and cooperative participants only. G is readable and is not a secret or proof of ownership.
3. **Acquire (linearization point A).** In one receipts `BEGIN IMMEDIATE` transaction: reconcile, require `stopped = 0` and no PENDING/UNCERTAIN intent, then `UPDATE fail_stop SET stopped = 1, reason = :G WHERE singleton = 1 AND stopped = 0` (rowcount 1), COMMIT. A is the COMMIT; durability is SQLite's commit point for the receipts file in its configured journal mode (the adapter sets no journal-mode or synchronous PRAGMA; only the gate sets WAL and synchronous=FULL at GATE:258-266). If not confirmed: no gate call, poison, stop.
4. **Effect commits (all under the armed stop; none clears it).** Gate reservation (GATE:432-522, admission DB), W1 PENDING, W2 ledger append (LED:314-497, ledger DB), the S9 HALT receipt, and **two changes to the 6838692613 design**: the S10 definite-rejection commit writes only the rejected receipt, and the S13 W3 commit writes only ACCEPTED, the accepted receipt, the sequence and the assignment identity. **Neither contains the clear.** Any non-confirmed outcome of any effect commit: poison, no further gate/W2/W3/release call; the stop is durably present on both branches.
5. **Release (linearization point R).** Only after the final effect commit is confirmed, a new receipts `BEGIN IMMEDIATE` transaction: require `stopped = 1 AND reason = :G` (the in-memory G), require the attempt's terminal record to be present in this store (the ACCEPTED intent and accepted receipt, or the rejected receipt), then `UPDATE fail_stop SET stopped = 0, reason = NULL WHERE singleton = 1 AND stopped = 1 AND reason = :G` (rowcount 1), COMMIT. R is the COMMIT. Confirmed release returns the result. Release rollback-before-commit: stop stays, poison, manual. Release ambiguous: poison; see G3 for why both branches are accepted only under a contract change.
6. **Participants that must check the stop.** At 0ab7358, non-test source gives these receipts/admission/ledger entry points (from `git grep` at 0ab7358): legacy `OfflineAuthenticatedAdapter.accept()` (ADP:504-721; checks `fail_stop` at ADP:531-535); the proposed `accept_signed()`; the unused writers `_advance_sequence` (ADP:435-444) and `_record_receipt` (ADP:475-502), which have no callers in the tree but do not check the stop; `_init_receipts` (ADP:335-418; `INSERT OR IGNORE` cannot overwrite an existing row); `OfflineAdmissionGate.reserve` (GATE:365-532), whose only non-test caller is the B2.2 simulator (SIM:287) and which has no reference to the receipts store; and `CheckpointLedger.record_event` (LED:280-497), whose only non-test caller is the adapter (ADP:656). Several test modules also reference these tables directly and are outside the check. **The stop fences only participants that perform the check.** Direct gate or ledger callers, tests, other receipts databases and file-level writers are outside it unless protected files change (G4). This is a statement about cooperative participants, not global exclusion.
7. **Startup and restart.** The current constructor runs `_init_receipts`, `_schema_preflight` and `_reconcile` but does not consult `fail_stop` (ADP:73-83), so an ungated instance can be constructed under a stop but cannot admit through `accept()`. Proposed: a gated constructor refuses while `stopped = 1` or any PENDING/UNCERTAIN intent exists; restart never parses or adopts G and never releases. No recovery API.
8. **Exact fail-closed rules.** A participant admits only if, inside its own `BEGIN IMMEDIATE`, it positively reads the provisioned `fail_stop` row with `stopped = 0` and reconcile passes. Each of the following refuses with no admission write: `stopped = 1` with any reason (G, BLOCKED suffix or foreign); row missing or duplicated; store unreadable, locked past the timeout, malformed or failing `PRAGMA`/`SELECT`; reconcile error (ADP:198-209, ADP:270-274); the store not carrying the proposed provisioning marker (rule 9). A refusal writes nothing to the stop.
9. **Failures of the stop mechanism itself.** (a) Arming fails or is ambiguous: no effect issued (G3, C1). (b) Stop unreadable or corrupt: rule 8, refuse; never treat unreadable as released. (c) **Deleted or replaced store:** today a missing receipts file is recreated by `_init_receipts` with `fail_stop (1, 0, NULL)` (ADP:336, ADP:389), which silently reads as "released". Reconcile then catches it only when adapter-origin ledger events exist (ADP:310-312); a store deleted between arming and W2 resets the stop undetected. The proposed fix is that admission paths never create the receipts store: a manual provisioning step writes a marker, and admission refuses when it is absent (G4, P-3). This is fail-closed against accidental deletion, not against a hostile file-level writer (§9). (d) Release fails: stop stays or release is ambiguous (rule 5). (e) A foreign stop reason is never released, because release matches the exact in-memory G.
10. **Crash windows.** Before A: nothing durable from this attempt. Between A and the final confirmed effect: stop present, manual. Between the final confirmed effect and R: stop present, manual, at an availability cost only; durable state is a confirmed admission or rejection. **After R lands but before success is observed** (crash, or COMMIT returns an error after landing): the stop is released and the admission was already confirmed durable by the earlier effect commit. Upstream may not know the result; a resubmission of the same identity is refused by global replay before any guard (6838692613 S6(b)) or by gate identity checks (GATE:453-479), and manual inspection is diagnostic only.
11. **Critical evaluation.** Gains: no ambiguous admission-effect commit can release the global stop, on either branch, and no correctness step depends on a write after a failure. Costs: one extra receipts commit per admission; every crash between A and R needs manual recovery; the existing O3 availability trade-off (a global ledger revision race becomes UNCERTAIN under an armed stop) is unchanged. Limits: cooperative participants on one receipts database only; the gate and ledger are not fenced by the stop unless protected source changes; HALT-to-commit, schema-to-WAL and cross-db atomicity are not affected. Rejected alternatives: (i) writing a stop after ambiguity (to the same store or to the ledger's per-checkpoint UNCERTAIN event, LED:309-310, LED:412-414) is a later write to a store that may be failing and is per-checkpoint, not global; (ii) holding an OS file lock or the receipts write lock in a poisoned process gives exclusion only while that process lives, so it is not durable and is not claimed; (iii) a heartbeat or lease would turn a crash into an automatic release after expiry, which is recover-forward and is not proposed.

### G3. Achievability verdict

**The literal requirement ("every ambiguous result stops all future admission") is NOT achievable under this failure model** (any commit may land and then raise, may fail after COMMIT is issued without landing, the process may die at any instant, any store may become unwritable, and processes share no memory), by this mechanism or any other whose stop is durable state. Proof by indistinguishability: a fresh process can decide only from durable state, so two runs that leave byte-identical durable state must get the same decision.

- **Counterexample C1 (first durable write).** P1 issues the arming COMMIT at A; the commit does not land, COMMIT raises (for example, an I/O error), and P1 then dies or cannot write anywhere. The durable state is identical to "P1 never attempted". P2 must be allowed in that state (otherwise no admission could ever start), so P2 proceeds although P1's result was ambiguous. This applies to the first durable write of any protocol, including one that uses a separate stop store, since that write can fail the same way.
- **Counterexample C2 (last blocked-to-allowed transition).** P1's release COMMIT at R lands and then raises (or P1 dies right after it lands). The durable state is identical to a confirmed release, after which P2 must be allowed (the "Confirmed W3: ACCEPTED, guard cleared: allowed" row of 6838692613 §8). P2 proceeds although P1's result was ambiguous. Moving the release later only moves the problem to the new last write. The only escape is never to release automatically: every admission ends with a stop that a human clears. That meets C2 at the cost of one manual action per admission, and still does not meet C1.

**Minimum contract change (a decision for Skippy and Chief; not adopted here).** Keep the stronger requirement for every commit that carries or may carry an admission effect, and state two exactly bounded exemptions:
Here an *admission effect* is a gate reservation, an intent-journal row or state change, an accepted receipt, a sequence or assignment-identity change, or a ledger event. Rejected and uncertain receipts are audit records, not admission effects.
- **E1 (pre-effect).** An ambiguous commit is exempt when it precedes every admission effect of the attempt: the arming commit at A, and the pre-arming rejected/uncertain receipt commits of 6838692613 S5-S7. Both branches (stop or audit receipt present, or no trace) contain no admission effect. The instance is poisoned. A stricter variant arms before S5, so those receipts are also written under the stop; that narrows E1 to the arming commit alone, at the cost of an arm and a release for every pre-check rejection.
- **E2 (post-confirmation release).** An ambiguous release commit at R is exempt provided every effect commit of the attempt was confirmed before R was issued and R changes nothing but `fail_stop`. Both branches (stop present, or released) are confirmed-consistent durable states. The instance is poisoned. A stricter variant, E2', has no automatic release (manual release per admission) and removes E2 at a large availability cost.

Under E1 and E2, the G2 mechanism gives: **every ambiguous commit that a cooperative participant on the bound receipts database issues after arming and before release leaves the global stop durably present, on both branches.** That covers every admission-effect commit, including the S10 rejection-receipt and S13 W3 commits that §G identified. This is **not** Alternative B: B lets other participants proceed after an ambiguous rejection-cleanup or W3 commit, while E1/E2 do not. It is also not the literal Alternative A. Recording E1/E2 (or E2'), Alternative A as worded, or Alternative B remains Chief's decision with Skippy. No claim of global exclusion is made from process-local poison, and none is made for non-cooperative participants.
